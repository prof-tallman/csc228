# SQL Injection Workshop — Instructor Notes

## Audience and Goal

This activity is designed for small business owners who are comfortable with business operations but may know very little about computer security.

The goal is not to turn participants into SQL experts. The goal is to help them discover, through guided experimentation, that a web application can accidentally treat **user-supplied data as database instructions**.

The activity uses three scenarios:

1. **READ** — view records the user should not be able to see.
2. **DELETE / DISRUPT** — interfere with legitimate business activity.
3. **MODIFY / ACCOUNT TAKEOVER** — alter another customer's account information and redirect a password-reset workflow.

The suggested order is:

**READ → DELETE → MODIFY**

This order works well because it increases the business impact gradually. READ introduces the core concept with relatively low stakes. DELETE shows operational disruption. MODIFY is saved for last because it is likely to feel the most personal and consequential: the participant changes another customer's account information and sees how that could lead to account takeover.

---

# Core Teaching Idea

Throughout the activity, keep returning to one question:

> **What did the computer think you meant?**

Participants type text into an ordinary-looking web form. They think they are supplying data. The vulnerable application places that data directly into a SQL statement, where part of the input can become an instruction.

A useful summary is:

> **Injection happens when data and instructions are mixed together.**

Do not begin by explaining all of the SQL syntax. Let participants first observe strange behavior, then reveal enough of the query for them to reason about what happened.

---

# Recommended Activity Structure

Each scenario should use several levels of discovery.

## Level 1 — Normal Use

Participants use the feature exactly as intended.

## Level 2 — Strange Input

Participants try a few unusual characters or values and observe unexpected behavior.

## Level 3 — Reveal the SQL

Show the SQL statement the server constructed.

## Level 4 — Guided Challenge

Give participants a goal and a partial hint rather than the complete solution.

## Level 5 — Business Consequence

Translate the technical result into something that matters to a business owner.

## Level 6 — Fix and Retest

Switch to the parameterized version of the query and have participants try the same input again.

The secure version should ideally accept the malicious-looking text as ordinary text rather than merely reject it. This makes the central lesson visible:

> **The secure application does not have to understand whether the input is suspicious. It simply refuses to treat the input as SQL instructions.**

---

# Scenario 1 — READ

## Business Story

The participant is using an ordinary customer-search feature in a business portal.

The page might contain:

```text
Customer Search

Company name:
[ Acme                         ]

[ Search ]
```

A normal search for:

```text
Acme
```

returns the expected customer record.

The vulnerable server constructs something similar to:

```sql
SELECT id, company, contact, email
FROM customers
WHERE company LIKE '%Acme%';
```

---

## Learning Objective

Participants discover that a search field intended to contain a company name can alter the logic of the database query.

The business consequence is unauthorized disclosure of customer information.

This maps naturally to **confidentiality**.

---

## Level 1 — Normal Search

Have participants search for several ordinary values:

```text
Acme
Dental
Supply
```

Ask:

- What does the application appear to be doing?
- What information do you think the server sends to the database?

Do not explain SQL injection yet.

---

## Level 2 — Strange Input

Give them a small list of unusual values to try:

```text
'
%
Acme'
```

They should observe that punctuation can produce behavior that differs from an ordinary search.

Depending on how the application is configured, an apostrophe may produce a SQL error or some other unexpected response.

Ask:

> Why would punctuation in a company name affect the application this much?

---

## Level 3 — Reveal the Query

Turn on the instructor/debug view and show the query generated by a normal search:

```sql
SELECT id, company, contact, email
FROM customers
WHERE company LIKE '%Acme%';
```

Then show what happens when the user types:

```text
Acme'
```

Point out that the application is not keeping the user's input separate from the SQL statement.

Ask:

> Which part came from the programmer, and which part came from you?

Then ask:

> Which characters in your input are now being interpreted as SQL instead of as part of a company name?

---

## Level 4 — Return Every Customer

Give the participants a partial payload:

```text
' OR ______ --
```

Provide the hint:

> Fill in an expression that is always true.

They should eventually reach:

```text
' OR 1=1 --
```

The resulting query will resemble:

```sql
SELECT id, company, contact, email
FROM customers
WHERE company LIKE '%' OR 1=1 -- %';
```

The important discovery is that the `WHERE` condition is now true for every row.

### Instructor Question

Ask:

> Did we guess anyone's password?

The answer is no. The attack changed the meaning of the database query.

---

## Optional READ Challenges

These can be given as challenge cards.

### Challenge A — Return Every Record

Goal:

> Make the application return every customer.

Hint:

```text
' OR ______ --
```

### Challenge B — Return a Selected Range

Goal:

> Can you make the application return only customers whose ID is greater than 3?

A guided form might be:

```text
' OR id > ___ --
```

The purpose is not to teach sophisticated SQL. It is to show that once input becomes part of the query, the user can begin controlling the logic.

### Challenge C — Explain the Apostrophe

Ask participants to explain in their own words:

> Why does `'` matter?

A good answer is that it can end the text value the programmer intended and allow following characters to become SQL syntax.

---

## Business Debrief

Translate the result into business terms.

Possible data exposed by a similar flaw could include:

- customer contact information;
- addresses;
- account records;
- order history;
- invoice information;
- internal notes;
- employee records.

Ask:

> If a customer-search box returned every customer in your system, what information in your own business would become visible?

---

## Secure Version

Vulnerable:

```python
sql = f"""
SELECT id, company, contact, email
FROM customers
WHERE company LIKE '%{search}%'
"""
```

Secure:

```python
sql = """
SELECT id, company, contact, email
FROM customers
WHERE company LIKE ?
"""

cursor.execute(sql, (f"%{search}%",))
```

Now have participants enter the same attack again:

```text
' OR 1=1 --
```

The database should search literally for a company containing those characters.

### Key Teaching Point

The parameterized query tells the database:

> This part is data.

The database no longer has to decide whether the input looks dangerous.

# Scenario 2 — DELETE / DISRUPT

## Business Story

Do not present this as an artificial "Delete Customer" feature.

Instead, use a normal business function such as **Cancel Order**.

A customer portal might show:

```text
ACME OFFICE SUPPLY
Open Orders

Order #1042    Printer paper       $428.00     [Cancel Order]
Order #1057    Toner cartridges    $612.00     [Cancel Order]
```

The application intends to let the logged-in customer cancel only an order belonging to that customer.

A vulnerable query might be:

```sql
DELETE FROM orders
WHERE id = 1042
AND customer_id = 7;
```

A production system might use an `UPDATE` to mark an order as cancelled rather than physically delete it. Either implementation can work for the lesson.

---

## Learning Objective

Participants discover that SQL injection can disrupt normal business operations, not merely expose information.

This maps naturally to **availability** and operational impact.

---

## Level 1 — Cancel One Legitimate Order

Have participants cancel one of their own test orders normally.

Show the resulting SQL:

```sql
DELETE FROM orders
WHERE id = 1042
AND customer_id = 7;
```

Explain the intended rule:

> Customer 7 may cancel order 1042 only if order 1042 belongs to customer 7.

---

## Level 2 — Identify the Protection

Ask:

> Which part of the query prevents Acme from cancelling another customer's order?

They should identify:

```sql
AND customer_id = 7
```

This helps them see that authorization is being enforced by part of the query.

---

## Level 3 — Guided Injection

Give them a target:

> Can you cause the condition to match orders beyond the one you selected?

A guided example is:

```text
1042 OR 1=1 --
```

This can transform the query into something similar to:

```sql
DELETE FROM orders
WHERE id = 1042 OR 1=1 --
AND customer_id = 7;
```

The comment marker causes the intended customer restriction to be ignored.

---

## Level 4 — Show the Business Effect

Do not stop with:

```text
18 rows affected
```

Show an employee-facing operational dashboard before the attack:

```text
TODAY'S OPEN ORDERS

18 orders
$12,486 pending revenue

Packing:             8
Awaiting shipment:   6
Scheduled delivery:  4
```

After the attack:

```text
TODAY'S OPEN ORDERS

0 orders
$0 pending revenue
```

Then show:

```text
WAREHOUSE QUEUE

No orders awaiting fulfillment.
```

Ask:

> What happens tomorrow morning when employees rely on this system to decide what to pack and ship?

---

## Alternative: Cancel Rather Than Delete

A more realistic implementation may be:

```sql
UPDATE orders
SET status = 'Cancelled'
WHERE id = ...
```

This is pedagogically useful because nothing has technically disappeared from the database.

Before:

```text
18 Open Orders
```

After:

```text
18 Cancelled Orders
```

The business effect may still be severe because fulfillment systems stop processing those orders.

### Teaching Point

> An attacker does not have to erase data to disrupt a business. Changing the state of legitimate transactions can be enough.

---

## Alternative Business Scenarios

If orders do not fit the audience, use the same concept with:

- cancelling appointments;
- deleting or cancelling service tickets;
- removing pending quotes;
- cancelling reservations;
- removing items from a fulfillment queue;
- cancelling scheduled deliveries.

An appointment system is especially easy to understand:

Before:

```text
Tomorrow

9:00    Smith
10:00   Garcia
11:30   Patel
1:00    Johnson
2:30   Williams
```

After:

```text
Tomorrow

No appointments scheduled.
```

Ask:

> How many hours of revenue disappeared even though no password was stolen?

---

## Business Debrief

Possible consequences include:

- lost sales;
- missed shipments;
- idle employees;
- unhappy customers;
- rescheduling costs;
- damaged reputation;
- accounting reconciliation;
- emergency restoration from backups.

Emphasize that the database may still exist and the webserver may still be running. The business can nevertheless be seriously disrupted.

---

## Secure Version

Vulnerable:

```python
sql = f"""
DELETE FROM orders
WHERE id = {order_id}
AND customer_id = {logged_in_customer_id}
"""
```

Secure:

```python
sql = """
DELETE FROM orders
WHERE id = ?
AND customer_id = ?
"""

cursor.execute(sql, (order_id, logged_in_customer_id))
```

Have participants retry the same malicious order ID.

The application should now interpret the entire value as an order identifier rather than SQL logic.

# Scenario 3 — MODIFY / ACCOUNT TAKEOVER

## Why This Scenario Comes Last

This should probably be the final SQL exercise.

READ demonstrates information exposure.

DELETE demonstrates operational disruption.

MODIFY is likely to feel the most significant because it connects database manipulation with identity, trust, and control of a customer account.

This makes it an effective climax for the SQL portion of the workshop.

---

## Business Story

The participant is logged into the customer portal as:

```text
ACME OFFICE SUPPLY
Account #1007
```

The account page allows the customer to update legitimate profile information:

```text
Point of Contact
Maria Lopez

Email
maria@acme.example

Mailing Address
2450 Harbor Blvd.
Costa Mesa, CA 92626

[ Save Changes ]
```

The application correctly knows that the logged-in user is Acme.

The intended rule is:

> Acme may update only Acme's record.

---

## Learning Objective

Participants discover that an attacker may not need to steal another customer's password first.

By altering another customer's account email or recovery information, the attacker may redirect an account-recovery process and gain control afterward.

This maps naturally to **integrity**, authentication, authorization, and account recovery.

---

## Level 1 — Make a Legitimate Change

Have participants change their own email address.

The vulnerable server constructs something similar to:

```sql
UPDATE customers
SET email = 'newaddress@acme.example'
WHERE id = 7;
```

Ask:

> Which part comes from the form?

Then ask:

> Which part makes sure Acme changes only Acme?

Answer:

```sql
WHERE id = 7
```

---

## Level 2 — Introduce Another Customer

Show another record:

```text
Customer #3
Mountain View Dental

Point of Contact:
Dr. Susan Chen

Email:
susan@mountainview.example

Mailing Address:
1820 Main Street
Irvine, CA 92614
```

Give the challenge:

> You are still logged in as Acme. Can you change information belonging to Mountain View Dental?

Do not give the full payload immediately.

---

## Level 3 — Reveal the Vulnerable Query

Show:

```python
sql = f"""
UPDATE customers
SET email = '{email}'
WHERE id = {logged_in_customer_id}
"""
```

Then show the SQL resulting from a normal update:

```sql
UPDATE customers
SET email = 'newaddress@acme.example'
WHERE id = 7;
```

Give the hint:

> Your text is inserted between quotation marks. Can you end the value early and supply a different `WHERE` clause?

---

## Level 4 — Change the Point of Contact

The first modification challenge can be relatively harmless:

```text
Dr. Susan Chen
        ↓
John Smith
```

This proves that another customer's record can be changed.

The exact payload should be provided gradually or as a hint card rather than shown immediately.

---

## Level 5 — Change the Mailing Address

Next, change:

```text
1820 Main Street
Irvine, CA 92614
```

to a clearly fake workshop address such as:

```text
500 Attacker Avenue
Testville, CA 90000
```

Ask:

> What business processes might trust this address?

Possible answers:

- shipping;
- replacement credit cards;
- checks;
- invoices;
- tax documents;
- legal notices;
- account-verification mail.

This expands the lesson beyond "someone changed a field in a database."

---

## Level 6 — Change the Account Email

Now make the consequence more serious.

Change:

```text
susan@mountainview.example
```

to:

```text
takeover@evil.example
```

A possible injected value in this isolated training environment is:

```text
takeover@evil.example' WHERE id = 3 --
```

This can transform:

```sql
UPDATE customers
SET email = 'USER_INPUT'
WHERE id = 7;
```

into:

```sql
UPDATE customers
SET email = 'takeover@evil.example' WHERE id = 3 --'
WHERE id = 7;
```

The attacker's `WHERE` clause replaces the application developer's intended restriction.

---

## Level 7 — Simulated Password Reset

Return participants to a fake login screen.

Choose:

```text
Forgot Password?
```

Enter the Mountain View Dental account.

The application should display something like:

```text
Password reset message sent to:

takeover@evil.example
```

No real email needs to be sent.

Then put this question on the projector:

> **Who controls the account recovery process now?**

This is the business-impact moment.

---

## Critical Debrief: Authentication vs. Authorization

Ask:

> Did the attacker crack Susan's password?

No.

Ask:

> Was the attacker properly logged in?

Yes — as Acme.

Then explain:

**Authentication** answered:

> Who are you?

The system correctly knew:

```text
You are Acme.
```

**Authorization** was supposed to enforce:

```text
You may change only Acme.
```

The injection altered the SQL enforcing that rule.

A useful summary is:

> The attacker did not defeat the login system. They changed the database instruction that decided which account could be modified.

This is especially valuable for small-business audiences because cybersecurity is often reduced to passwords and MFA.

---

## Secure Version

Vulnerable:

```python
sql = f"""
UPDATE customers
SET email = '{email}'
WHERE id = {logged_in_customer_id}
"""

db.execute(sql)
```

Secure:

```python
sql = """
UPDATE customers
SET email = ?
WHERE id = ?
"""

db.execute(sql, (email, logged_in_customer_id))
```

Now enter the exact same malicious-looking value:

```text
takeover@evil.example' WHERE id = 3 --
```

Mountain View Dental should remain unchanged.

Instead, Acme's own email may literally become:

```text
takeover@evil.example' WHERE id = 3 --
```

That is an excellent demonstration.

The database is effectively saying:

> Those characters are part of the email address you gave me. They are not instructions.

# Suggested Overall SQL Progression

The three activities now form a coherent sequence:

```text
READ
Can I see information I should not see?

        ↓

DELETE / DISRUPT
Can I interfere with legitimate business activity?

        ↓

MODIFY
Can I alter another person's account and redirect control?
```

They also provide a natural introduction to the CIA triad:

| Scenario | Security Property | Business Meaning |
|---|---|---|
| READ | Confidentiality | Someone sees information they should not see |
| DELETE / DISRUPT | Availability | Normal operations are interrupted |
| MODIFY | Integrity | Trusted information is changed |

The MODIFY exercise can then extend beyond the CIA triad into authentication, authorization, and account recovery.

---

# Suggested Instructor Pacing

## Before Any Injection

Let participants use the application normally.

Do not begin with SQL syntax.

Ask them what they believe the application is doing behind the scenes.

---

## During Discovery

Prefer hints such as:

> What happens if you end the text value early?

or:

> Which part of this query decides which rows are affected?

rather than immediately giving them the complete input.

The goal is guided discovery, not memorization of attack strings.

---

## When Showing SQL

Use visual highlighting if possible.

For example:

```text
PROGRAMMER'S SQL:
SELECT ... WHERE company LIKE '%

USER INPUT:
' OR 1=1 --

PROGRAMMER'S SQL:
%'
```

Then show the combined statement.

This helps nontechnical participants understand where the vulnerability comes from.

---

# Suggested Instructor Questions

Use business-oriented questions throughout.

After READ:

> What information in your business would be damaging if every customer could see it?

After DELETE:

> Which business process would stop if these records suddenly disappeared or were cancelled?

After MODIFY:

> Which fields in your systems are trusted by other business processes?

And finally:

> If the application trusts a database value, what else might trust it too?

Examples include:

- password reset;
- shipping;
- billing;
- payroll;
- account recovery;
- customer notifications;
- approvals.

---

# Reset and Safety

This lab should operate only against disposable workshop data.

Recommended controls:

- Run the vulnerable application inside a disposable container.
- Use no real customer information.
- Use no real passwords or API keys.
- Provide a **Restore Workshop Database** button.
- Reset the database between groups if necessary.
- Do not connect the exercise database to production systems.
- Do not reuse the vulnerable application outside the training environment.

For the DELETE scenario in particular, the ability to restore the sample database instantly is useful pedagogically as well as operationally.

---

# Final Takeaway

End the SQL section with one sentence:

> **The application was supposed to treat what we typed as data. The vulnerability occurred because it allowed our data to become part of the database instructions.**

Then show the common solution:

> **Keep code and data separate by using parameterized queries.**

The participants do not need to leave knowing how to write SQL.

They should leave understanding why a seemingly harmless text box can become a serious business risk when user input is mixed directly into a command.
